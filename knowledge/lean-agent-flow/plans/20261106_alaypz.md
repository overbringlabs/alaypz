# Plan — Alaypz app (2026-11-06)

Scope: `decisions/20261106_alaypz_scope.md` (S1–S8) +
`decisions/20261106_persistence_and_views.md` (persistence, `/leaderboard`,
`/:player_name`, unique names with access-string reclaim). Design grounding:
`research/20261106_liveview12_footguns.md`.

Architecture: server-authoritative game process (one GenServer per game); every
client — player and spectators — renders the pushed state on a canvas
`phx-hook` driven by `push_event`; the canvas tweens between the last two
server states. The lobby view owns the `lobby` PubSub subscription and
`send_update`s per-card LiveComponents; the focused game surface is a component
with an `.AlaypzCanvas` hook. Player name is client-only state (localStorage),
unique per the database (D-20261106-02).

## Notes

- Cards are LiveComponents (operator ask), **not** stream items: the lobby view
  owns the `lobby` subscription and `send_update`s each card (research:
  components are not processes; streams belong to the view).
- Card mini-boards are small canvases (200 cells × N games as DOM is heavy);
  the same `.AlaypzCanvas` hook scaled down; `/leaderboard` final boards use
  it in static mode.
- `push_event` flushes with the view's diff (research): the tick that updates
  state calls `push_event/3` to the canvas hook, keeping the DOM diff near zero.
- Name flow (D-20261106-02): submit → DB validation; new name → access string
  shown once (not auto-stored client-side); taken name → reclaim form; match
  reclaims, mismatch rejects. Salted per-row hash, timing-safe verify,
  stdlib `:crypto`.
- `/:player_name` is declared after the specific routes; unknown names and
  unknown paths both render the not-found state.
